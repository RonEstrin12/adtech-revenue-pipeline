# AdTech Revenue Pipeline: תיאור הפרויקט

## הרקע העסקי

אתר תוכן מרוויח בעיקר ממכירת שטחי פרסום. רוב השטחים האלה לא נמכרים ישירות למפרסמים. הם נמכרים דרך כמה שותפי פרסום פרוגרמטי (SSP, ad exchange ורשתות), ובכל רגע כל אחד מהם מתחרה על המקומות הפנויים בדף.

בכל בוקר כל שותף מדווח כמה הוא הרוויח לאתר אתמול. הבעיה היא שכל שותף מדווח בדרך אחרת:

- **ערוץ שונה:** אחד חושף REST API, אחר שם קובץ CSV בתיקייה, ושלישי שולח מייל.
- **שדות בשמות שונים:** `imps` אצל אחד, `Impressions` אצל אחר.
- **פורמט תאריך שונה:** `YYYY-MM-DD` מול `DD/MM/YYYY`.
- **מטבע שונה:** דולר אצל אחד, שקל אצל אחר, ולפעמים שניהם באותו קובץ.
- **נתונים מלוכלכים:** רווחים מיותרים, ערכים חסרים, שורות כפולות, מספרים שליליים, תאריכים שלא קיימים בלוח השנה, וסימן מטבע בתוך שדה מספרי.

בלי צינור נתונים מסודר, מישהו בצוות פותח כל בוקר כמה קבצים ומעתיק אותם לגיליון. זה איטי, וטעות של סימן ₪ אחד יכולה להזיז את דוח ההכנסות היומי באלפי דולרים.

**מטרת הפרויקט:** צינור נתונים יומי שאוסף את הדוחות של כל השותפים, שומר את המקור כמו שהוא, מנקה ומאמת אותו, טוען אותו למחסן נתונים, מריץ בדיקות איכות עם התראות, ומפרסם סיכום יומי ב-Google Sheets. כל זה צריך לרוץ אוטומטית, ושיהיה בטוח להריץ אותו שוב.

## מבט על

```
 Partner A (REST API) ─┐
                       ├─► S3 raw ─► ניקוי ואימות ─► Postgres ─┬─► ניתוח SQL
 Partner B (קובץ CSV) ─┘                │                     ├─► בדיקות איכות ─► התראות
                                        ▼                     └─► Google Sheets
                                  rejected_rows
```

הכול רץ פעם ביום מתוך GitHub Actions (שלב 8). דיאגרמה מפורטת יותר, עם הסטטוס של כל רכיב, נמצאת ב-[ARCHITECTURE.md](ARCHITECTURE.md).

## השותפים המדומים (שלב 1)

שותף אמיתי לא נותן גישה ל-API שלו לפרויקט לימודי, ולכן הפרויקט כולל שני שותפים מדומים שמתנהגים כמו האמיתיים, כולל הבעיות.

| | Partner A | Partner B |
|---|---|---|
| ערוץ | REST API עם אימות `x-api-key` | קובץ CSV שנופל לתיקיית `inbox/` |
| שדות | `day, site, unit, imps, rev_usd` | `Date, Website, Placement, Impressions, Revenue, Currency` |
| תאריך | `YYYY-MM-DD` | `DD/MM/YYYY` |
| מטבע | דולר | בעיקר שקל, ואתר אחד בדולר |
| לכלוך מכוון | רווחים ואותיות גדולות בשם האתר, הכנסה חסרה (`null`), שורה כפולה | חשיפות שליליות, סימן מטבע בתוך מספר, התאריך `2026-13-45`, שורה כפולה |

שני השותפים מוכרים את אותם שלושה אתרים (`news.co.il`, `sports.co.il`, `recipes.co.il`) בשלוש יחידות פרסום (`top_banner`, `sidebar`, `video_mid`).

**הנתונים נוצרים מ-seed לפי התאריך:** אותו יום תמיד מחזיר בדיוק אותו דוח. זו החלטה מכוונת, כי בלי דטרמיניזם אי אפשר לבדוק טענה כמו "הרצה כפולה לא משכפלת הכנסות". הקוד ב-`src/mock-partners/`.

## איסוף ל-S3 raw (שלבים 2 ו-2.5)

שלב ה-ingest (`src/ingest/`) לוקח את הדוח של כל שותף ושומר אותו **בדיוק כפי שהתקבל** ב-S3, מחולק לפי שותף ותאריך:

```
s3://raw/partner=a/date=2026-11-25/fetched_at=2026-11-26T06-54-54-218Z.json
s3://raw/partner=b/date=2026-11-25/fetched_at=2026-11-26T06-54-54-436Z.csv
```

### החלטות התכנון

- **המקור נשמר בלי שינוי.** אם יתגלה באג בניקוי, מריצים מחדש מה-raw בלי לבקש מהשותף לשלוח שוב. במחלוקת על כסף אפשר גם להוכיח מה השותף באמת שלח.
- **הקבצים רק מתווספים, וכפילויות מזוהות לפי התוכן.** כל העלאה שומרת sha256 של הקובץ. אם הקובץ האחרון של אותו שותף ואותו יום זהה, לא מעלים שוב. אם שותף שולח דוח מתוקן, הוא נשמר כגרסה חדשה עם `fetched_at` משלו לצד הישנה.
- **אפשר להריץ אותו יום כמה פעמים.** אחרי העלאה, הקובץ של Partner B עובר ל-`processed/`. בהרצה חוזרת המערכת מזהה אותו שם ומחזירה `unchanged` במקום להיכשל. התיקון הזה נוסף בשלב 2.5.
- **ניסיון חוזר רק כשהוא יכול לעזור.** בקשה ל-Partner A מנוסה שוב אחרי שגיאת רשת, 5xx או timeout, עם המתנה שגדלה בין ניסיונות. על 4xx לא מנסים שוב, כי מפתח שגוי או תאריך לא תקין לא יסתדרו מעצמם. לכל ניסיון יש מגבלת זמן (`PARTNER_A_TIMEOUT_MS`), כך ששותף תקוע לא תוקע את כל הריצה.
- **שותף אחד שנכשל לא עוצר את האחרים.** הריצה ממשיכה עם שאר השותפים, אבל מסתיימת בקוד יציאה שאינו 0, כדי שה-scheduler וההתראות ישימו לב.
- **אותו קוד מקומית ובייצור.** מקומית `S3_ENDPOINT` מצביע על S3Mock בתוך Docker. בייצור המשתנה לא מוגדר וה-AWS SDK מדבר עם S3 אמיתי.
- **תאריכים נבדקים בקפדנות.** ב-`src/lib/dates.ts` תאריך תקין רק אם הוא קיים בלוח השנה. `2026-02-30` נדחה, למרות ש-`Date.parse` של JavaScript מקבל אותו בשקט.

## ניקוי ואימות (שלב 3)

המטרה היא להפוך שני פורמטים שונים **לשורה אחת אחידה**:

| עמודה | משמעות |
|---|---|
| `date` | תאריך ISO. תאריך שלא קיים בלוח השנה נדחה |
| `partner` | `a` או `b` |
| `site` | שם האתר בלי רווחים ובאותיות קטנות |
| `ad_unit` | יחידת הפרסום |
| `impressions` | מספר החשיפות. ערך שלילי או חסר נדחה |
| `revenue_usd` | ההכנסה בדולרים, אחרי הסרת סימני מטבע והמרה משקלים |
| `raw_key` | הקובץ ב-S3 שממנו הגיעה השורה, כדי שתמיד אפשר יהיה לחזור למקור |

**שורה פגומה לא נמחקת בשקט.** היא נשמרת ב-`rejected_rows` יחד עם הסיבה לדחייה. כך אפשר למדוד כמה מהדוח של כל שותף נפסל, ולהתריע כשהאחוז קופץ.

הפקודה `npm run validate -- <date>` קוראת את קובץ ה-raw האחרון של כל שותף ויום. היא כותבת שני קבצים ל-S3 לכל שותף ויום:

```
s3://raw/clean/partner=b/date=2026-11-25/rows.json       ← שורות תקינות
s3://raw/clean/partner=b/date=2026-11-25/rejected.json   ← שורות שנדחו + סיבה
```

השמות של הקבצים קבועים, ולכן הרצה חוזרת דורסת אותם ולא מוסיפה שורות. ב-2026-11-25, למשל, יצאו 15 שורות תקינות ו-5 שנדחו: 2 כפולות, תאריך לא קיים, הכנסה חסרה וחשיפות שליליות. כל לכלוך שהוזרק בכוונה נתפס.

שתי ברירות מחדל עדיין מחכות לאישור:
- **שער ההמרה משקל לדולר:** כרגע שער קבוע מ-`FX_ILS_PER_USD`, ברירת מחדל 3.7. השער ששימש נשמר בכל `rows.json`. אפשר להחליף אותו בשער יציג יומי בפונקציה אחת, `src/lib/fx.ts`.
- **אזור הזמן שקובע מה זה "אתמול":** `REPORT_TZ`, כרגע UTC. לאתר ישראלי כנראה מתאים `Asia/Jerusalem`.

## השלבים הבאים

- **שלב 4, טעינה ל-Postgres (נבנה):** `npm run migrate` יוצר את הטבלאות מקובץ SQL פשוט, ו-`npm run load -- <date>` טוען את ה-clean zone. השורות התקינות נכנסות ל-`revenue_daily` עם מפתח טבעי של partner, date, site ו-ad_unit, וההכנסה נשמרת כ-NUMERIC כדי שסכומים יהיו מדויקים. השורות שנדחו נכנסות ל-`rejected_rows` יחד עם השורה המקורית כ-JSONB. כל שותף ויום נטענים בטרנזקציה אחת שמוחקת אותם משתי הטבלאות ומכניסה מחדש, כך שהכנסה לעולם לא נספרת פעמיים: שתי טעינות של 2026-11-25 נתנו בדיוק אותן 15 שורות ואותו סכום, 2208.320271 דולר. אם `rows.json` ו-`rejected.json` לא הגיעו מאותו קובץ raw, הטעינה של אותו שותף ויום נעצרת.
- **שלב 5, ניתוח SQL (נבנה):** קובץ SQL שני, `002_analysis_views.sql`, מוסיף views מעל `revenue_daily`: סיכום יומי, הכנסה, חשיפות ו-eCPM לפי שותף, אתר ויחידת פרסום, שינוי בהכנסה של כל שותף לעומת אתמול (בדולרים ובאחוזים, עם `LAG`), ואחוז השורות שנדחו מכל מה שהשותף שלח. כשאין חשיפות ה-eCPM הוא NULL ולא חלוקה באפס, והשוואה נעשית רק מול היום הקודם בלוח השנה, כך שחור בנתונים לא מושווה ליום ישן יותר. הפקודה `npm run report -- <date>` מדפיסה את הסיכום: ב-2026-11-25 ההכנסה הייתה 2,208.32 דולר ב-eCPM של 2.68, Partner A עלה ב-10.15% ו-Partner B ירד ב-7.98%. השאילתה נפרדת מההדפסה, כדי ששלב 7 ישתמש בה ל-Google Sheets.
- **שלב 6, בדיקות איכות והתראות:** שותף שלא דיווח, אחוז שורות נדחות חריג, וקפיצה חדה בהכנסה לעומת אתמול.
- **שלב 7, Google Sheets:** סיכום יומי לגיליון שהצוות העסקי כבר עובד איתו.
- **שלב 8, תזמון:** GitHub Actions מריץ את כל השרשרת כל בוקר. לשם כך צריך S3 ו-Postgres מאוחסנים וסודות בריפו.

## איך מריצים

```bash
npm install
cp .env.example .env
docker compose up -d                # Postgres + S3Mock

npm run partner-a                   # טרמינל נפרד: ה-API של Partner A
npm run partner-b -- 2026-11-25     # Partner B מניח קובץ CSV
npm run ingest -- 2026-11-25        # שמירת שני הדוחות ב-S3
npm run raw:ls                      # מה יש ב-raw zone
npm test                            # בדיקות יחידה
```

## מילון מונחים

- **Impressions (חשיפות):** כמה פעמים מודעה הוצגה.
- **Revenue (הכנסה):** הכסף שהחשיפות הכניסו.
- **eCPM:** הכנסה לכל 1,000 חשיפות (`revenue / impressions * 1000`). זה מדד המחיר המרכזי, והוא מאפשר להשוות בין שותפים ובין יחידות פרסום.
- **Display / Video:** סוג המודעה. וידאו נמכר ב-eCPM גבוה בהרבה.
- **Idempotent:** פעולה שאפשר להריץ שוב ושוב עם אותה תוצאה. זה העיקרון שעליו כל הצינור בנוי.
- **Raw zone:** האזור ב-S3 שבו נשמרים הקבצים המקוריים בלי שום שינוי.
- **rejected_rows:** השורות שנפסלו בניקוי, יחד עם הסיבה לפסילה.
